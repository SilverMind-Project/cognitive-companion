# Knowledge Delivery and Cognitive Care

Patterns and architectural standards for the curated Knowledge Repository, Info Cards, Quizzes, Senior RAG Q&A, and Pipeline Builder knowledge steps (see `/home/sriram/code/nanai/notes/cc/cc-rag.md` for background). For general backend layering, typing, time, logging, and testing rules, follow `/home/sriram/code/nanai/cognitive-companion/.claude/skills/engineering-standards/SKILL.md`. For Vue/Vuetify UI rules, follow `/home/sriram/code/nanai/cognitive-companion/.claude/skills/front-end/SKILL.md`.

## 1. Service-layer ownership (no ORM or MinIO logic in routers)

Routers under `backend/routers/{knowledge.py,info_cards.py,quizzes.py,knowledge_interactions.py,knowledge_layouts.py}` must be thin HTTP adapters: validate input, enforce `require_permission(...)`, extract actor via `actor_from_auth(auth)` (`backend/core/auth.py`), call a service on `app.state`, and return a typed Pydantic `response_model`.

All business logic, status state machines, SQLAlchemy sessions, and MinIO side-effects live in `backend/services/knowledge/`:
- `backend/services/knowledge/ingestion_service.py` (`KnowledgeIngestionService`): document CRUD, image attachment CRUD, single-session chunking and Triton embedding, re-embed retry job, and MinIO prefix cleanup (`knowledge/{doc_id}/`).
- `backend/services/knowledge/info_card_service.py` (`InfoCardService`): info card CRUD, slot image upload/source-image binding/variant rendering via `ImagePipeline`, layout-change re-rendering and `min_images` validation, approval/archival transitions, and delete guards.
- `backend/services/knowledge/quiz_service.py` (`QuizService`): quiz and question CRUD, atomic question reordering, question image upload/source-image binding/variant rendering and presigned URL enrichment, approval validation (at least one question; valid choices for `multiple_choice`; non-empty `expected_answer` for `open_ended`), archival transitions, and delete guards.
- Responsibility modules mixed into those services (same public methods, shared injected dependencies): `backend/services/knowledge/document_embedding.py` and `backend/services/knowledge/document_images.py` (ingestion), `backend/services/knowledge/info_card_slots.py` (info cards), `backend/services/knowledge/quiz_questions.py` (quizzes). Put new chunking, slot, or question code there rather than growing the service file past about 500 lines.
- `backend/services/knowledge/interaction_service.py` (`KnowledgeInteractionService`): paginated `{items, total}` queries for `SeniorKnowledgeQuery`, `QuizSession` (with detail and responses), `InfoCardDelivery`, and `TagAnalyticsOut`, using timezone-aware UTC bounds (`datetime.combine(d, time.min, tzinfo=UTC)`). Exposed identically through `backend/routers/knowledge_interactions.py` and MCP tools for BFF/MCP parity.
- `backend/services/knowledge/query_service.py` (`KnowledgeQueryService`): vector similarity search over `approved` document chunks + constrained LLM synthesis + audit logging to `senior_knowledge_queries`.
- `backend/services/knowledge/content_generation.py` (`ContentGenerationService`): LLM-assisted paraphrase, quiz draft generation, single-question regeneration, voice instruction suggestion, and generous open-ended answer grading.
- `backend/services/knowledge/delivery_service.py` (`KnowledgeDeliveryService`): runtime delivery of info cards across PWA WebSocket, e-ink (`async_get_object` / `async_upload_bytes`), and Gemini Live voice. Its responsibility modules: `backend/services/knowledge/quiz_delivery.py` (quiz start, completion, timeout, question fanout), `backend/services/knowledge/quiz_answers.py` (locked answer recording from either channel), `backend/services/knowledge/quiz_messages.py` (quiz wire vocabulary), and `backend/services/knowledge/delivery_context.py` (template context, persona composition and release). The scheduler is bound after construction with `attach_scheduler`.

## 2. Startup validation and single-session ingestion

1. **Startup model-ID validation:** `wire_knowledge` (`backend/bootstrap/knowledge.py`) must verify at startup that `knowledge.answer_model`, `knowledge.paraphrase_model`, and `knowledge.quiz_generation_model` exist in `app.state.llm_model_registry` (or log a structured error / fail fast when configured models do not match `llm.models[*].id` in `config/settings.yaml`). Never reference an unregistered model alias. Being in `llm.models` is not enough: the inference server must also serve the model. `backend/services/llm_model_health.py` probes each server's `/v1/models` (the admin LLM health page and a one-shot startup job both use it) and logs `llm_model_not_served` as an error for a model a knowledge feature depends on.
2. **Single-session chunk and embed:** `KnowledgeIngestionService._chunk_and_embed` must update `doc.status = "chunked"` (and `doc.updated_at = datetime.now(UTC)`) on a `KnowledgeDocument` row loaded within the same SQLAlchemy `Session` that inserts `KnowledgeDocumentChunk` rows and commits. Never mutate a `KnowledgeDocument` instance attached to an outer uncommitted session, or documents will remain stuck in `'uploaded'` and re-embed every 10 minutes forever.
3. **Commit-before-purge and 409 delete guards:** Before deleting an `InfoCard` or `Quiz`, check whether any rule's `PipelineStep` (`info_card` or `quiz_start`, enabled or disabled rule) references it via `rule_ids_referencing` in `backend/services/knowledge/references.py` (compares the config id as text, never a cast). Historical `InfoCardDelivery`, `QuizSession`, and `QuizResponse` references are enforced by `ON DELETE RESTRICT`: map the `IntegrityError` at commit to `ConflictError` (HTTP 409) telling the caregiver to archive instead; never duplicate the foreign key as a read-then-write count. Purge MinIO objects only after `db.commit()` succeeds, and a purge failure after commit is logged, not raised.
4. **Re-embed keeps approval:** `KnowledgeIngestionService.reembed_document` re-chunks unchanged content without demoting an approved document; only an edit to `source_text` sends a document back through review. `_chunk_and_embed` embeds outside any transaction, then locks the row and abandons the write if the text changed meanwhile.
5. **pgvector in raw SQL:** write `CAST(:vec AS vector)`, never `:vec::vector`. SQLAlchemy `text()` does not bind a parameter followed by `::`, so the literal reaches PostgreSQL and every similarity search fails.
6. **Image object keys:** quiz question images live under `quizzes/{quiz_id}/q{question_id}__*` and info card slots under `info_cards/{card_id}/slot{index}__*` (the `__` delimiter keeps `q1` from matching `q12`). Never key by ordinal, and never purge a slot's `original_object_name` that points into `knowledge/{doc_id}/` (`owned_object_names` filters to the owner's prefix).

7. **Quizzes save atomically:** the quiz editor saves details and the whole ordered question list in one `PATCH /quizzes/{quiz_id}` with `questions` (`QuizService.update_quiz_with_questions` in `backend/services/knowledge/quiz_question_list.py`; `PUT /quizzes/{quiz_id}/questions` is the list-only form) and creates a quiz with its questions in one `POST /quizzes`. Never save a quiz with one request per question: a mid-way failure leaves a half-saved quiz. Removing questions needs `quizzes:delete`, checked under the quiz lock. Reorder takes the complete order or 422s.
8. **Choice ids:** a choice id is non-blank and unique within its question (schema-validated); the editor assigns the next free letter (`frontend/src/components/knowledge/quizChoices.js`), and `content_generation.normalize_choices` fixes drafted choices.
9. **Tag filters are any-of:** list endpoints take a repeatable `tag` parameter matched with array overlap, the same as the `knowledge_query` step.

## 3. Multimodal voice + PWA synchronization and voice lifecycle

1. **Always compose with base persona:** Every voice delivery (`deliver_info_card`, `start_quiz_session`, `interactive_prompt`, and `guided_task`) must compose its `voice_instruction` via `VoiceInstructionConfig.compose(step_type, base_instruction=<llm.realtime.system_instruction>, step_override=..., resource_override=..., context=..., directive=...)`. Passing a per-delivery instruction without `base_instruction` wipes out the companion's identity, household context, and tool-calling instructions on Gemini Live reconnect. `KnowledgeDeliveryService` receives the base at construction; a step uses `knowledge_delivery.compose_voice_instruction(...)`, which returns None when the step adds nothing (so the live session is not reopened).
2. **Release the persona the delivery owns:** A delivery's instruction is owned by `voice_owner_key(delivery_type, ref)` (`quiz_start:{session_id}`, `info_card:{delivery_id}`), taken from the prompt metadata. When a quiz completes or times out, or an info card is dismissed, call `ws_manager.release_voice_instruction(owner)`. It reaches every live audio handler, restores the base persona only where that owner's instruction is active (a card closing never strips a running quiz), ends an open realtime session between turns (never mid-sentence), and never wakes an idle handler.
3. **Never swap a realtime session in place:** `AudioSessionHandler` changes the system instruction by ending the session and replaying the prompt into the next one; the receiver is bound to its session, so an in-place reconnect strands the prompt on an unread session. A prompt that changes the instruction while a turn is still being spoken (an orchestrator prompt awaiting its reply, or the model mid-turn) waits for `turn_complete`, with every later prompt behind it; otherwise a card delivered just before a quiz is cut off unheard. Orchestrator prompts are instructions to the agent ("Read this card aloud..."), never bare content, or the agent answers them as if the senior had spoken.
4. **Enable microphone on voice-interactive delivery:** When `start_quiz_session` or `AgentSessionVoice.speak_step` injects a voice prompt expecting a spoken response from the senior, broadcast `{"type": "enable_microphone"}` over `ws_manager` so `CompanionView.vue` activates audio recording if the microphone is idle.
5. **Synchronize PWA and voice across every question:**
   - `start_quiz_session` must include the first question's multiple-choice options (or open-ended prompt) in the initial voice prompt injected into Gemini Live, and `QuizDialog.vue` must auto-advance from the intro screen to Question 1 when a question payload arrives or after a brief gentle countdown so voice and screen never show different states.
   - `submit_quiz_answer` must lock the `QuizSession` row (`with_for_update()`) only to check status and ordinal and to write the answer (never across open-ended grading, a model call, or a broadcast), reject terminal sessions (`completed`, `abandoned`, `timed_out`), return the recorded result for a repeat of an answered question, reject an answer for a question that is not current with the current question, and return `explanation`, `completed`, and `next_question` (`question_ord`, `question_type`, `question_text`, `choices`, `total`) so the `submit_quiz_answer` MCP tool gives Gemini Live everything needed to speak Question N+1 without a second tool call. With no caller latency, `latency_ms` is the time since the question was presented (`last_activity_at`).
   - When the tablet answers a session that was delivered with voice, inject a brief orchestrator update (what was chosen, whether it matched, and the explanation) so the voice agent responds to the answer as its mode says and asks the next question in lockstep. Gate on "delivered with voice", never on `ws_manager.active_connections`: notification-only tablets count as connections, and the prompt would open a paid realtime session for a tablet-only quiz.
6. **Quiz timeout safety:** The delivery service schedules and cancels its own `quiz_timeout_{session_id}` job (a bound `handle_session_timeout` with only the session id as an argument; the job store is in-memory). `complete_quiz_session` cancels it. The timeout handler only transitions sessions still `started` or `in_progress` (never overwriting `completed`), broadcasts `quiz_timeout` to close `QuizDialog.vue`, releases the persona, and resumes the pipeline. The `quiz_start` step parks until a backstop past the timeout, so the session is terminal before anything downstream runs.
7. **Resuming the owning pipeline:** `resume_owning_pipeline(scheduler, execution_id)` schedules the resume for now under the executor's own `resume_{execution_id}` job id. It runs off the tool-call path and replaces the executor's `wait_until` fallback, so the pipeline resumes exactly once. Never call the async `PipelineExecutor.resume` without awaiting it.
8. **Eager-load what delivery reads:** a step that closes its session before calling delivery must load `Quiz.questions` and `InfoCard.image_slots` with `selectinload`; a lazy load on the detached row raises.
9. **Dedupe queries:** Always use `.order_by(QuizSession.completed_at.desc()).limit(1).scalars().first()` (never `.scalar_one_or_none()`) when checking recent completed sessions within `dedupe_hours`.

## 4. Pipeline Builder integration and RAG link

1. **`knowledge_query` step:** The Pipeline Builder connects rules to the curated Knowledge Repository through `backend/steps/builtin/knowledge_query.py` (`category="reasoning"`, `gate_safe=True`), distinct from `semantic_memory_query` (camera scene observations). It renders `{{ }}` templates in `query_text` and `tags`, calls `services.knowledge_query.answer(query, tags=..., top_k=..., min_similarity=...)` (blank overrides inherit `knowledge.retrieval_top_k` / `knowledge.min_similarity`, so pipelines and voice answer alike), and emits `query_text`, `answer_text`, `answered_via`, `has_answer`, `top_similarity`, `source_document_ids`, `source_chunk_ids`, `chunks`, and `query_id` (set only with `log_interaction`, channel `pipeline`). `has_answer` is true only for `answered_via="rag"`: synthesis replies with the `NO_ANSWER` sentinel when the context lacks the answer, and the service maps it to `no_answer`; never report a refusal sentence as an answer.
2. **Template rendering at delivery time:** `info_card` and `quiz_start` steps pass `template_data=pipeline_data`, `trigger_vars=make_trigger_vars(trigger)`, and `senior_id=resolve_person_id(config, pipeline_data)` to delivery, which renders `{{ }}` templates on `card.title`, `card.body_text`, `card.voice_instruction`, `quiz.title`, `quiz.intro_voice_template`, `quiz.voice_instruction`, and the step's `voice_instruction`. `senior_name` resolves from `HouseholdMember.name`, or an empty string, so a placeholder never reaches the senior.
3. **Cool-off promotion:** Both `InfoCardStep.execute` and `QuizStartStep.execute` must check `if config.get("trigger_cooloff", True): result_data["_cooloff_triggered"] = True` so rules that deliver info cards or quizzes respect `rule.cool_off_minutes`.
4. **Templated `person_id`:** `resolve_person_id(config, pipeline_data, trigger_vars)` renders a templated `person_id` itself (nothing renders step config before a step runs) and returns None (logging `person_id_template_unresolved`, field name only) when the template does not resolve: a named person resolves to that person or nobody, never to whoever is first in the pipeline. A blank `person_id` still uses the pipeline fallbacks.
5. **Configurable output keys:** a step that writes its result under a configurable key declares its `output_schema` under the default key plus `"x-output-key": {"config_field": ..., "default": ...}`; the editor's variable autocomplete (`instanceOutputSchema` in `frontend/src/components/pipeline/steps/stepMeta.js`) follows each step's configured key.
6. **Dedicated step config components:** Every built-in senior-care step (`info_card`, `quiz_start`, `guided_task_start`, `knowledge_query`, `interactive_prompt`) has a dedicated structured Vue config editor (keys and scalar defaults pinned to the backend by `backend/tests/steps/test_step_config_ui_parity.py`; leave out a default the backend derives from settings, such as `summon_timeout_s`) under `frontend/src/components/pipeline/steps/` registered in `steps/index.js` with canvas summary `chips` and `STEP_DOT_COLORS` in `stepMeta.js`. Never leave senior-care steps on the raw JSON `GenericPluginConfig.vue` fallback.

## 5. Clinical dementia-care UX standards

1. **Errorless Learning and Gentle Reminiscence mode (`interaction_mode: "gentle" | "standard"`, a `quiz_start` config key):** the mode's directive (`quiz_gentle_directive` / `quiz_standard_directive` in `config/knowledge_voice.yaml`) is appended after any caregiver override, so a custom persona can change the tone but never turns gentle mode into graded testing. Clinical neuropsychological research (Baddeley & Wilson, 1994; Clare et al., 2000; Woods et al., 2018 Cochrane Review on Reminiscence Therapy) demonstrates that overt testing and harsh error feedback ("Incorrect") trigger test anxiety, cortisol elevation, and withdrawal in people with dementia, and can reinforce false memory traces. Quizzes default to `"gentle"` (reminiscence/errorless-learning) mode:
   - Never display harsh red "Incorrect / Wrong" banners or percentage failure scores to the senior.
   - When the senior selects or speaks an unexpected answer in `"gentle"` mode, offer a warm, dignity-preserving cue or conversational reminder using the question's `explanation` ("That's a lovely thought! Here is a little reminder: ...") and allow moving forward comfortably without penalty, while still recording `is_correct` in `quiz_responses` for longitudinal caregiver cognitive-trend tracking.
2. **Multimodal dual-coding (visual + voice):** Seniors with dementia commonly have presbycusis (hearing loss) and reduced working-memory span. Every spoken prompt, info card, quiz question, or RAG answer (`KnowledgeAnswerWidget.vue`, `InfoCardDialog.vue`, `QuizDialog.vue`, and the guided-task companion widget) must pair warm, unhurried audio with high-contrast large typography (`>= 22px` body, `>= 28px` title), clear imagery when available, generous touch targets (`>= 64px` height), and a bounded auto-dismiss timer (`KnowledgeAnswerWidget.vue` defaults to 45s with a manual "Got it" button) so stale dialogs never block the screen forever.
